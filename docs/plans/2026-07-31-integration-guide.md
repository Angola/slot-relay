# サイト実装者向けの連携ガイドを作る

- 日付: 2026-07-31
- ブランチ: `docs/integration-guide`

## やりたいこと

予約フォームを作る人（genba-tsunagu.jp などサイト側の実装者）に
**URL を 1 本渡せば伝わる**ドキュメントを `docs/INTEGRATION.md` として用意する。

## 背景・なぜ

ステージング（`booking-api.stagehubs.net`）が動き、サイト側へ連携を依頼できる段階になった。
ところが、実装者に必要な情報が 4 か所に分散している。

| 場所 | 書いてあること |
| --- | --- |
| `README.md` | エンドポイント一覧 |
| `docs/DESIGN.md §5.2` | サイト側に置く設定 3 つ |
| `docs/DEPLOY.md §6` | 同上（重複） |
| `web/README.md` | 参照実装の読みどころ |

「まずこれを読んで」と言える 1 枚がなく、**毎回口頭で補う前提**になっていた。
とくに次の 3 点は説明しないと必ず事故る。

- **`Idempotency-Key` の発行規則** — 「予約 1 回につき 1 つ」「409 で選び直したら新しいキー」
  という規則が独特で、使い回すと二重予約防止が誤作動する
- **許可 Origin の事前登録** — 依頼側（API 運用者）が先に登録しないと、
  相手の実装が全部 403 になり、原因究明で時間を溶かす
- **秘密を渡さない線引き** — `ADMIN_API_KEY` や `TURNSTILE_SECRET_KEY` を
  「連携に必要だろう」と渡してしまう事故を防ぐ

## 方針

読者を**サイト側の実装者ひとり**に絞る。運用者向け（`DEPLOY.md`）や
設計の一次情報（`DESIGN.md`）は繰り返さず、リンクする。

載せるもの:

- 全体像の図（サイト → API → Google）
- 受け取る値 3 つ／**受け取らない値**
- 3 リクエストの流れと `curl` 例
- `Idempotency-Key` の規則
- エラーコード一覧と画面での出し分け
- Turnstile の組み込み
- 連携前に API 運用者がやること（許可 Origin の登録）

エラーコードは `ApplicationController::ERROR_STATUSES` と、実際に
`failure(:...)` / `render_error(:...)` で返している値を突き合わせて書く（推測しない）。

### 重複をどうするか

`DESIGN.md §5.2` と `DEPLOY.md §6` に同じ環境変数 3 つが書かれている。
消さずに `INTEGRATION.md` へのリンクを足すにとどめる。
両者の読者（設計を追う人／運用者）にとっても「サイト側に何を渡すか」は必要な情報で、
消すと文脈が切れるため。一次情報は `INTEGRATION.md` とする。

## 経緯・メモ

- 「ドキュメントをどう共有すればいいか」という問いから出発した。
  リポジトリが public なので URL を送るだけで済むが、入口が無いのが問題だった。
- `CLAUDE.md` の「`docs/` に最低限維持するファイル」にも追加する。

## 積み残し

- 英語版は作らない（当面の読者は日本語話者のみ）
- 予約フォームの UI 設計指針（デザイン・文言）は範囲外。サイト側の裁量に任せる
